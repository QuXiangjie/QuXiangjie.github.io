Whose identity does the agent use?

When an agent calls an external system (a product catalog, an ERP, a CRM), the first auth question isn't "OAuth or API key?" It's whose identity is making the call. OAuth and SSO are only ways to get an identity. Once you know whose identity you need, the rest of the design mostly follows.

There are two patterns. Most real assistants need both.

Pattern A: a service account

The agent uses one shared service-account token for every user. It sits in a server environment variable, and there's one per deployment.

CATALOG_TOKEN = os.environ["CATALOG_SERVICE_TOKEN"]
headers = {"Authorization": f"Bearer {CATALOG_TOKEN}"}
ProsCons
The simplest to build. No per-user credentials to manage.Permission logic lives in your code, disconnected from the target system's own permission model.
Works even if the target system doesn't support OAuth.A prompt injection can lead to over-reach, because the only defense is your code, not the target system.
Audit logs show only the service account, so you can't tell who did what.

Use it only when all three are true:

  • Every user sees the same data. There are no row-level permissions.
  • The data isn't sensitive. A leak would cost nothing real.
  • You don't need to trace who performed an action.

Examples: a product-catalog lookup, public docs, the shared part of a knowledge base. One trap: a catalog can be public while its pricing isn't. Contract or customer-specific prices are per-user data and belong in Pattern B.

Pattern B: the user's own identity

Every request reaches the external system with the current user's token. With the Claude Agent SDK, I build a fresh ClaudeAgentOptions per request and seal the token inside the tool's closure. The model calls the tool but never sees the credential.

from claude_agent_sdk import ClaudeAgentOptions, create_sdk_mcp_server, tool

def make_erp_server(user_token):
    @tool("get_orders", "List the current user's orders", {"status": str})
    async def get_orders(args):
        # user_token is captured here; it never enters the prompt
        rows = await erp_get("/orders", token=user_token, params=args)
        return {"content": [{"type": "text", "text": json.dumps(rows)}]}
    return create_sdk_mcp_server("erp", tools=[get_orders])

def build_options(user_token, user_id):
    return ClaudeAgentOptions(
        mcp_servers={"erp": make_erp_server(user_token)},
        allowed_tools=["mcp__erp__*"],
        tools=[],                  # turn off built-in tools (Bash, Read, ...)
        strict_mcp_config=True,    # only the servers passed here
        setting_sources=[],        # ignore settings files on disk
        cwd=f"/work/{user_id}",    # one working directory per user
    )
ProsCons
The target system enforces permissions. The agent can never exceed what the user could do themselves.More work to build. Users have to authorize first, or IT has to help set it up.
Prompt injection can't widen access: an over-reaching request is simply rejected by the target system.The OAuth route still means managing refresh tokens.
Audit logs record the actual user.

Use it for orders, customers, invoices, finance: any business data whose permissions differ by user.

Three ways to get the user's token

In order of preference:

RouteWhat the backend storesWhen
SSO token exchange (e.g. Entra ID on-behalf-of)No per-user credentials. Only the app's own client credential; downstream tokens are short-lived and thrown away.The target system's API accepts tokens from your company IdP. First choice.
OAuth 2.0A refresh token per user, encrypted.External SaaS such as Salesforce or GitHub.
User API keyA long-lived key per user, in a secrets vault.Legacy systems that only support API keys. Last resort.

A note on the first row: "the target uses company SSO" has to mean its API trusts the IdP's tokens, not just that people sign into its web UI with SSO. If only the UI is wired up, you're on the OAuth row.

The same idea applies to MCP servers. The MCP authorization spec forbids token passthrough: a server must not forward the client's token to an upstream API. It gets its own token for the downstream system, which is exactly what a token exchange does.

OAuth's two tokens

LifetimeStored?If it leaks
Refresh tokenLongYes, encryptedThe user or IT revokes it in one click, and the whole chain dies.
Access tokenShort, about an hourNo, used and discardedWait for it to expire.
  • For a confidential client, a refresh token can't call business APIs on its own. It only becomes an access token together with the client secret.
  • Each refresh can return a new refresh token. Write it back over the old one (rotation protection).
  • Treat invalid_grant as "needs re-authorization" and send the user through the connect flow again.

Do these in either pattern

  • Tokens never appear in the prompt, options.env, code, git, or logs.
  • Secrets come from environment variables or a vault. In .mcp.json, reference them as ${VAR}.
  • Turn off built-in tools you don't need with tools=[].
  • In multi-turn conversations, check who owns a session before resuming it, so user A can't resume user B's session.
  • Give each user their own working directory.

The two patterns together

One agent can carry both:

mcp_servers={
    "catalog": catalog_server,               # Pattern A: service account
    "erp":     make_erp_server(user_token),  # Pattern B: user identity
}

Catalog questions go through the service account. Business data goes through the user's identity. This is the standard architecture for an assistant that mixes shared data with per-user data. Permissions are enforced by the target system, not by the prompt. "Only show this user their own orders" in a system prompt is not access control.

The decision

Is the data the same for everyone, non-sensitive, and untracked?
├─ yes → Pattern A: service account
└─ no  → Pattern B: the user's identity
         ├─ target API trusts the company SSO → token exchange (no per-user credentials)
         ├─ target supports OAuth 2.0         → store an encrypted refresh token
         └─ API key only                      → store the key, treat it as a high-risk asset
